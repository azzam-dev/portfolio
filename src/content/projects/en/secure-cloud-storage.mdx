problemOneLiner: "Every user's files in one database, one missing filter away from each other."

status: "in-progress"

surface:
  what: "A multi-user file storage web app where every row and every file is scoped to one account, and that scoping is enforced by the database rather than by application code. A face scan is offered as an alternative to typing a password."
  why: "Multi-tenant storage fails in one direction: a query that forgets a filter hands back somebody else's data. Putting the rule inside Postgres means the check cannot be skipped by whichever endpoint gets added next, or by whoever writes it."
  forWhom: "People storing personal documents who need their account to be an enforced boundary, not a convention the code is trusted to remember."

deep:
  layers:
    - id: "browser"
      label: "Browser"
      note: "Uploads files and, for face login, computes the descriptor locally. It is never sent anyone else's data to compare against."
    - id: "middleware"
      label: "Middleware"
      note: "Refreshes the session cookie and redirects unauthenticated requests before a protected page renders. Verifies the token against the auth server rather than trusting the cookie."
    - id: "app"
      label: "Next.js App"
      note: "Server Components and Server Actions. Every protected page re-checks the session even though the middleware already did — deliberate redundancy, not an oversight."
    - id: "auth"
      label: "Supabase Auth"
      note: "Issues and verifies sessions. Face login enters here through a one-time token, so a session has exactly one way of coming into existence."
    - id: "rls"
      label: "Row Level Security"
      note: "Every table is scoped to auth.uid() inside Postgres. Authorization lives here, not in route handlers."
    - id: "edge"
      label: "Edge Function"
      note: "The only caller permitted to compare a capture against other accounts, and the only place worth rate limiting."
    - id: "pgvector"
      label: "pgvector"
      note: "Stores 128-number descriptors with an HNSW index on L2 distance. No images are kept."
    - id: "storage"
      label: "Supabase Storage"
      note: "A private bucket for the files. Downloads are issued as 60-second signed URLs."
  architectureNotes: "The layers are arranged around one rule: the browser is never trusted with anything belonging to another account. That is why authorization sits in Postgres instead of in route handlers, and why the single operation that genuinely has to read across accounts — matching a capture against every enrolled descriptor — is pushed out of the application into a database function only the service role may execute. The Edge Function exists to be the one narrow door to it. For context, this is a rewrite: the original was a PyQt5 desktop app on a local MySQL install, where a single-user machine supplied that isolation for free. Moving to the browser meant rebuilding every one of those boundaries explicitly."
  decisions:
    - question: "Where should authorization live?"
      optionA: "In route handlers and page code, checked on each request."
      optionB: "In Postgres, as Row Level Security on every table."
      chosen: "Row Level Security."
      because: "An application-level check has to be repeated at every new call site, and the first one omitted is a data leak. RLS is enforced by the database regardless of which client asks or which query is written."
    - question: "How should a face be compared against every other enrolled account?"
      optionA: "Send the stored descriptors to the browser and compare them there."
      optionB: "A SECURITY DEFINER function with EXECUTE granted only to service_role, reached through an Edge Function."
      chosen: "The database function behind an Edge Function."
      because: "Any design where the browser can see other people's embeddings is a biometric data leak, whoever is asking. Keeping the comparison inside Postgres means the raw descriptors never leave it."
    - question: "Which distance should pgvector use for matching?"
      optionA: "Cosine distance."
      optionB: "L2, or Euclidean, distance."
      chosen: "L2."
      because: "It was built on cosine first and then changed. face-api.js documents its own reference threshold of 0.6 in Euclidean terms, so a cosine threshold is a number with nothing to calibrate it against."
    - question: "How should face login mint a session?"
      optionA: "signInWithOtp."
      optionB: "auth.admin.generateLink, then exchange the token through verifyOtp."
      chosen: "generateLink."
      because: "signInWithOtp sends a real email on every attempt, spending the mail quota on a flow that never needed a mailbox."
  challenges:
    - whatBroke: "A page that writes to the database and to storage as the signed-in user was reachable with no session at all."
      howDiagnosed: "The middleware kept a list of public routes and matched them by prefix. /register was on that list, so every path beneath it inherited the same exemption — and the post-signup step sits directly underneath it. Nothing failed loudly; the page simply rendered for a signed-out visitor."
      fix: "Public routes are now split by matching strategy. /login and /register match exactly, while /auth stays a prefix match on purpose, because /auth/confirm is opened from an email link before any session exists. The reason for the split is written beside the list so a later edit does not quietly undo it."
    - whatBroke: "Face enrollment never completed in Chrome. The model weights loaded, then the first descriptor call died on a missing binary."
      howDiagnosed: "TF.js registers its webgl and wasm backends at the same priority, so on a machine without WebGL it silently selected wasm — a backend this project ships no binaries for and never calls setWasmPaths() to locate. The code also began loading weights before tf.ready() had resolved, hitting a backend that was registered but not initialised."
      fix: "selectBackend() forces webgl, falls back to cpu when that fails, and awaits tf.ready() before any weight load. Verified working in Chrome."
  security: "Authorization is enforced in Postgres rather than in application code: every table carries Row Level Security scoped to auth.uid(). The middleware verifies the session with getUser() instead of getSession(), so the token is checked by the auth server rather than trusted from the cookie. The one operation that must cross accounts — matching a capture against all enrolled descriptors — runs inside a SECURITY DEFINER function with EXECUTE revoked from anon and authenticated and granted only to service_role, which makes the Edge Function the sole path to it. That endpoint is limited to 10 attempts per IP per five minutes and returns a single-use token rather than a session. Enrollment stores a 128-number descriptor and nothing else: an earlier version uploaded a JPEG for a profile thumbnail, and once the thumbnail was dropped that upload was retaining a biometric image nothing read, so it was cut at the source. Files sit in a private bucket and leave only as 60-second signed URLs. This is access control, not end-to-end encryption: the server can read stored files, and the design does not claim otherwise."
  whatIdImprove:
    - "There are no automated tests — no runner, no test files. Everything has been verified by hand in a browser and with SQL against the live project, which is exactly the kind of coverage that does not survive a refactor."
    - "Face login is a convenience, not a second factor: a matching face alone is enough to sign in. Making it real two-factor authentication would mean pairing it with a password, and I would rather name it accurately than claim a property the design does not have."
